# Rift environment provider

The server registers `rift` with `experimental_environments`; BB owns picker UI, thread launching, setup/teardown and durable lifecycle attempts. The host adapter owns native Git/Rift processes and filesystem receipts. The app entry adds scoped overrides below the generated plugin settings form. There is no separate launch page.

Settings: plugin-wide defaults → project override for fetch/starting branch/dependency reuse + machine override for executable → explicit host request. Overrides live in plugin KV storage, are parsed on read, and share RPC validation with the UI and CLI. Empty machine paths request automatic runtime management; null overrides inherit defaults. Successful receipts retain their original starting branch even when settings change.

Create: BB path key → deterministic copy ID → copy lock → recover completed receipt if present → source lock → validate original checkout and prepare the runtime → verify own or standard existing Rift registry → optionally fetch the selected origin branch → resolve exact tracking commit → durable target plan → Rift copy including ignored files → clean branch at the selected commit → optional exact-path cleanup of ignored generated directories → durable receipt → BB setup → agent launch.

A successful retry returns the recorded copy without fetching or resetting the agent's existing work. Interrupted partial creation remains recoverable. With fetching enabled, a failed fetch stops creation. Offline mode requires an existing tracking ref. Git reset/clean operations target only the verified new copy. Dependency cleanup protects tracked files and does not touch unrelated ignored directories. Existing `mainCommit` receipts and plans without options are parsed into the original origin/main defaults at the persistence boundary; new receipts store `startingBranch` and `startingCommit`.

Removal resolves the durable plan, refuses descendants, records the predicted retained path, and invokes Rift removal. Partial unregistered copies are renamed into `.retained`. Repeated removals recover from the same plan. No garbage collection runs. Archival has no automatic retirement. Rebuilding unavailable copies refuses to replace independent history.

SDK declarations are generated from the installed BB version and currently match BB 0.43.0 (SDK 0.4.84). Host tests use the public 0.4.53 runtime. The native provider workflow was originally verified in Nightly; relocation was rebuilt and checked in BB 0.43.0.

Runtime ownership: `runtime.ts` resolves explicit user-managed overrides or a versioned executable in the host's persistent plugin data directory. First creation ensures installation only after receipt recovery and source validation. Picker inspection never downloads; missing Rift remains available because setup occurs inside creation. RPC `runtime` and `bb rift runtime` share installation/status/update behavior; the settings section displays those results.

Runtime update trace: explicit update or daily maintenance → per-data-directory in-process queue → recheck persisted attempt time → bounded npm metadata request → SHA-512 verified package → extract only native executable via tar stdout → capability probe → immutable version directory → atomic active-pointer write. Failed downloads preserve the previous pointer and runtime. Existing executables and registry ownership are independent of runtime installation. The queue relies on BB's single host worker per plugin; the daemon stops the old generation before starting its replacement. This avoids persistent installer locks after worker crashes. Copy/source filesystem locks remain separate because those protect native workspace operations and retained plans.

Automatic updates follow npm's stable `latest` tag and require the CLI capabilities used by the plugin. Capability checks do not establish compatibility with every future registry schema; future upstream registry changes may need a plugin update. Old managed executables remain available for recovery and in-flight operations. The hourly server schedule only attempts a daily update after a machine has used automatic setup; disconnected hosts are skipped. Explicit overrides are never installed or updated by the plugin.

The `experimental_environmentProviderInputs` slot registers BB's native `experimental_BranchPicker` beside the Rift environment dropdown. Server `riftInputsSchema` defaults to the resolved project options; a named selection overrides only this creation's starting branch. `starting-point.ts` resolves local heads or configured remote tracking refs and optionally fetches only the selected remote branch. Settings defaults remain origin branches; per-environment inputs support local and other remote branches. The selected ref and exact commit are recorded in the receipt. SDK 0.4.84 is the minimum for the host target shape used by this control.
